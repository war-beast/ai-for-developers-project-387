# Как участвовать в CallCalendar

Процесс публикации изменений: окружение, коммиты, ветки и PR. Соглашения
по коду и архитектуре — в [CODING_STANDARDS.md](./CODING_STANDARDS.md).

## Окружение

- Все версии инструментов зафиксированы в `mise.toml`; зависимости ставит `mise install`.
- Единая команда проверок: `mise run check` (сборка + линтеры + типы + тесты +
  дымовая проверка API + браузерный сценарий Playwright на реальном сервере).
  Она же вызывается из CI.
- Фоновые серверы (бекенд, Vite) описаны как демоны mise (`[daemons]` в mise.toml):
  `mise daemons start backend frontend`, `mise daemons logs backend`, `mise daemons stop ...`.
- Гит-хуки настроены через hk (`hk.pkl`), включая проверку commit-msg.

## Conventional Commits (обязательно)

Текст каждого коммита начинается с префикса: `feat:` — новая функция,
`fix:` — исправление бага; остальные типы (`chore:`, `docs:`, `refactor:`, `test:`)
используются по смыслу. Каждый коммит реализации заканчивается ссылкой на тикет
(`(#20)`), например: `feat: забронировать свободный слот (#20)`. Проверка
префикса выполняется хуком commit-msg (hk); ссылку на тикет проверяем на ревью.

Версию и `CHANGELOG.md` двигают только `feat:`, `fix:` и breaking change;
`chore:`/`docs:`/`refactor:`/`test:` в релиз не попадают. Поэтому меняется
поведение пользователя или контракт API — `feat`/`fix`, только сборка, CI,
тесты или рефакторинг без изменения поведения — остальные типы.
`CHANGELOG.md` и `.release-please-manifest.json` генерирует release-please
через Release PR в `dev` — руками не правим, Release PR нужно смержить.

## Ветки и PR

- Каждую новую задачу начинаем в новой ветке: `feat/<краткое-имя>` (git не
  допускает `:` в именах веток, поэтому префикс `feat:` пишется как `feat/`).
- Ветки `feat/` создаются только из `dev`.
- После завершения задачи — коммитим изменения (Conventional Commits) и делаем
  PR в ветку `dev` на GitHub.

`dev` — ветка по умолчанию: с неё начинаются задачи, в неё мержатся PR.
На неё завязаны деплой (`render.yaml`), CI и автозакрытие issue.

Любые изменения в `dev` и `main` попадают только через pull request: прямые
пуши в эти ветки запрещены защитой веток, в том числе для администраторов.
Ветка `main` обновляется PR из `dev`.

У каждого PR должно быть issue. Ссылка ставится в описании PR, и её проверяет
workflow `.github/workflows/pr-issue.yml`: без ссылки на существующее issue
(именно issue, а не другой PR) статус `pr-issue` красный. Мерж разрешён только
при зелёных статусах `pr-issue` и `check`.

PR в `dev` обязан закрывать своё issue: в описании нужна закрывающая ссылка
`Closes #12` (подходят также `Fixes #12` и `Resolves #12`). `dev` — ветка по
умолчанию, поэтому GitHub закрывает issue автоматически, как только PR
смержен в `dev`. PR в `main` (например, синхронизация `dev → main`) может
ссылаться через `Refs #12`, если issue уже закрыт.

Слияние PR выполняет только владелец репозитория. Агенты и остальные участники
готовят PR и дожидаются мержа владельцем — сами PR не сливают.

После мержа рабочая ветка удаляется: GitHub удаляет её автоматически (в
настройках репозитория включено удаление head-ветки при мерже), остаток в
локальном клоне убираем через `git branch -d <ветка>`.

## Авторевью PR

Каждый PR в `dev` получает автоматическое ревью
(`.github/workflows/opencode-review.yml`): общий комментарий с итогом и
замечания к строкам diff. Критерии и формат замечаний — в
[REVIEW.md](./REVIEW.md). Ревью независимое: отдельная модель не видит
историю реализации, работает только с checkout и собранным workflow
контекстом и не может менять код.

Ревью — **advisory**, не обязательная проверка: мерж не блокируется, но
каждое замечание нужно либо исправить, либо объяснить в PR, почему правка не
нужна. Форматирование проверяет линтер, авторевью его не комментирует.

Описание PR заполняется по `.github/pull_request_template.md`: проверки с
командами, ссылками на прогоны и SHA, риск, откат и влияние на данные.

## Бюджет запусков `/oc`

У команды `/oc` в PR/issue — **2 попытки**. Счёт ведётся по истории Actions,
поэтому Re-run и отмена тоже расходуют попытку. Третий запуск не вызывает
модель: workflow публикует `limit_exhausted`, последний SHA и ссылку на логи,
ставит лейбл `ready-for-human` и остаётся зелёным. Сбои `timeout`, `infra` и
`agent_failed` тоже публикуются с причиной и лейблом, но красным статусом.
Подробности и обоснование — [docs/adr/0004-pr-review-budget.md](./docs/adr/0004-pr-review-budget.md).
