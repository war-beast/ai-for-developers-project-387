# Тема разговора в записи

## Problem Statement

Владелец календаря видит в списке встреч тип встречи, имя и контакт гостя, а
также необязательный комментарий, но не видит, о чём будет разговор. Из-за
этого владельцу приходится открывать запись или уточнять тему отдельно, а гость
не может сообщить её при бронировании. Комментарий для этого не подходит: он
необязателен и не гарантирует, что тема будет указана.

## Solution

Добавить в запись обязательное поле «Тема разговора». Гость заполняет его при
бронировании; поле предзаполнено значением «Пожаловаться на трудную судьбу»,
чтобы отправка работала без ручного ввода. Длина — не более 250 символов
вместе с пробельными. Тема показывается гостю на экране подтверждения брони и
владельцу рядом с записью в списке встреч. Для записей, созданных до появления
поля, возвращается значение по умолчанию.

## User Stories

1. Как гость, я хочу видеть поле «Тема разговора» в форме бронирования, чтобы
   сообщить владельцу, о чём будет звонок.
2. Как гость, я хочу получить тему разговора уже заполненной значением по
   умолчанию, чтобы забронировать слот, не придумывая формулировку.
3. Как гость, я хочу изменить тему разговора перед отправкой, чтобы указать
   свою формулировку.
4. Как гость, я хочу видеть тему разговора на экране подтверждения, чтобы
   убедиться, что владелец получил её.
5. Как гость, я хочу, чтобы поле не принимало больше 250 символов вместе с
   пробельными, чтобы не получить ошибку после отправки.
6. Как гость, я хочу получить понятную ошибку рядом с полем, если тема пустая
   или слишком длинная, чтобы исправить ввод.
7. Как владелец, я хочу видеть тему разговора рядом с каждой записью в списке
   встреч, чтобы готовиться к звонку.
8. Как владелец, я хочу видеть значение по умолчанию у старых записей без
   темы, чтобы список оставался единообразным.
9. Как владелец, я хочу, чтобы тема разговора была отдельной от необязательного
   комментария, чтобы различать обязательную тему и свободные заметки гостя.
10. Как разработчик, я хочу видеть тему разговора в контракте API и в модели
    записи, чтобы клиенты и сервер одинаково понимали поле.
11. Как разработчик, я хочу, чтобы сервер проверял обязательность и длину темы,
    чтобы правило не зависело от клиента.
12. Как разработчик, я хочу, чтобы старые записи без темы не ломали ответы API,
    чтобы изменение было обратно совместимым.
13. Как разработчик, я хочу покрыть тему разговора unit-, API-, frontend- и
    e2e-тестами, чтобы регрессии ловились на уровне поведения.
14. Как разработчик, я хочу, чтобы smoke-проверка API отправляла тему, чтобы
    `mise run check` оставался зелёным.

## Implementation Decisions

- В контракте TypeSpec поле `topic` добавляется в `CreateBookingRequest` и
  `Booking` как обязательная строка.
- В модели записи тема хранится рядом с именем и email гостя. В сущности
  хранилища поле допускает `null`, чтобы читать записи, созданные до появления
  темы.
- Значение по умолчанию «Пожаловаться на трудную судьбу» и максимальная длина
  250 символов задаются константами в слое бизнес-логики.
- Сервер проверяет тему до обращения к типу встречи: пустая или состоящая
  только из пробельных символов тема отклоняется, длина проверяется по
  исходному значению вместе с пробельными. Перед сохранением тема обрезается.
- При чтении записи с пустой темой слой бизнес-логики подставляет значение по
  умолчанию, поэтому клиенты всегда получают непустую строку.
- Форма гостя получает поле с подписью «Тема разговора», значением по
  умолчанию и ограничением ввода 250 символов.
- Экран подтверждения и список встреч владельца показывают тему в виде
  «Тема разговора: …».
- Существующий необязательный комментарий сохраняется без изменений и
  остаётся отдельным полем.
- Хранилище в памяти, поэтому отдельная миграция не нужна; обратная
  совместимость обеспечивается подстановкой значения по умолчанию при чтении.

## Testing Decisions

- Тестируется внешнее поведение: какие значения принимает и возвращает API,
  что видит гость и владелец, а не внутреннее устройство классов.
- Unit-тесты бизнес-логики: пустая тема отклоняется, тема длиннее 250 символов
  вместе с пробельными отклоняется, тема обрезается, старая запись получает
  значение по умолчанию.
- Интеграционные тесты API: создание записи с темой возвращает её в ответе;
  запрос без темы даёт `400 validation_failed` с ошибкой по полю `topic`.
- Frontend-тесты: форма предзаполнена значением по умолчанию, отправляет тему,
  экран подтверждения и список встреч показывают тему.
- E2E-тесты: гость заполняет тему и видит её в подтверждении, владелец видит её
  в списке встреч.
- Smoke-проверка API отправляет тему при создании записи, чтобы проверка
  соответствовала обязательному контракту.
- Ориентиры: `BookingServiceTests`, `BookingsApiTests`, `EventTypePage.test.tsx`,
  `MeetingsPage.test.tsx` и сценарии в `frontend/e2e`.

## Out of Scope

- Редактирование темы после бронирования.
- Тема на уровне типа встречи или отдельный справочник тем.
- Поиск, фильтрация и сортировка встреч по теме.
- Подсчёт длины по графемам вместо символов строки.
- Постоянное хранилище и миграции данных.
- Изменение правил для необязательного комментария.

## Further Notes

- Поле называется «Тема разговора», чтобы не смешивать его с комментарием;
  формулировка закреплена в глоссарии.
- Значение по умолчанию намеренно задано и на клиенте, и на сервере: клиент
  показывает его гостю, сервер защищает контракт от запросов без темы.
