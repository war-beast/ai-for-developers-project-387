# Аудит Lighthouse по расписанию и задачи по находкам

Нужен регулярный, но не блокирующий проверки аудит опубликованного приложения:
Lighthouse собирает отчёт, агент разбирает его и превращает конкретные находки
во входящие задачи. Ручной запуск нужен для демонстрации и для проверки после
изменений, расписание — чтобы находки не терялись между релизами.

## Решение

- **Один workflow** `.github/workflows/opencode-audit.yml` с `schedule`
  (`0 3 * * 1`, понедельник 03:00 UTC = 06:00 МСК) и `workflow_dispatch`.
  Запуск идёт из default branch `dev`: GitHub выполняет `schedule` только с
  default branch, а `main` в этом репозитории обновляется из `dev` отдельным PR.
- **Lighthouse CLI 13.6.0** запускается по мобильному профилю для четырёх
  категорий (`performance`, `accessibility`, `best-practices`, `seo`) по
  `app_url` (по умолчанию — публичный Render-инстанс). Перед запуском
  приложение прогревается запросами к `/health`: бесплатный Render засыпает, и
  без прогрева Lighthouse падает на холодном старте.
- **Сырые данные — артефакт**: `lighthouse-report.json`, `lighthouse-report.html`,
  компактная выжимка, `audit-input.json`, сырой вывод агента и `report.md`.
  Срок хранения — 14 дней, как у `check` и `opencode-review`. Итог и ссылки на
  задачи публикуются в issue, поэтому срок жизни артефакта не влияет на
  доступность результата.
- **Агент — CLI `opencode run` + `GITHUB_TOKEN`**, а не GitHub Action. Экшен
  OpenCode v1.19.5, закреплённый в репозитории, принимает только
  `issue_comment` и `pull_request_review_comment`; для `schedule` и
  `workflow_dispatch` он не подходит. Режим `GITHUB_TOKEN` — эквивалент
  `use_github_token: true`: агенту нужны только `contents: read` (checkout) и
  `issues: write` (issues, комментарии, лейблы). `id-token`, `contents: write`
  и `pull-requests: write` не выдаются: аудит не меняет код и не открывает PR.
- **Отчётный issue** с меткой `audit-report` создаётся один раз; каждый прогон
  оставляет в нём комментарий с маркером `<!-- lighthouse-audit:<run_id> -->`.
  Повторный запуск того же прогона обновляет комментарий, а не создаёт второй.
- **Задача по находке** создаётся отдельным issue с метками `audit-finding` и
  `needs-triage`. Скрытый маркер
  `<!-- lighthouse-finding: <audit-id>@<url> -->` позволяет агенту найти
  существующую задачу до создания. Если задача уже есть и новых сведений нет,
  повторная задача и одинаковый комментарий не создаются; при новых данных
  (изменился score/детали) агент комментирует существующую задачу. Закрытую
  задачу агент не переоткрывает и новую не создаёт — решение за человеком.
- **Лимит три задачи за прогон**: `failingAudits` уже отсортированы по
  весомости; остальные находки перечисляются в отчёте. Это защита от лавины
  задач из одного отчёта.
- **Учебный режим** (`workflow_dispatch`, `mode=training`) разбирает
  подготовленный `.github/audit/training-lighthouse.json` или переданный
  `training_report`. Задача получает метку `training`, заголовок
  `[учебная находка]` и дисклеймер: это демонстрация, а не подтверждённый
  дефект. Учебная задача не получает `needs-triage` и не засоряет очередь
  реальных обращений.
- **PR по находке не создаётся**. Аудит только фиксирует проблему и предлагает
  действие; реализация — отдельное решение человека, при необходимости через
  `/oc`.

## Consequences

- `schedule` в GitHub — best-effort: запуск может задержаться, а Render может
  не проснуться за отведённые 8 попыток. В этом случае workflow публикует
  причину `lighthouse_unavailable` в отчётном issue и падает красным, а не
  создаёт ложную находку.
- Lighthouse измеряет конкретный прогон, поэтому scores могут колебаться.
  Дедупликация идёт по `audit-id` и URL, а не по точному score, поэтому
  колебания не плодят задачи.
- Задачи от бота не запускают `opencode-triage` (там стоит фильтр ботов).
  Метка `needs-triage` оставляет обращение входящим, но разбор инициирует
  человек. Это осознанный выбор: аудит не должен сам запускать цепочку
  согласования и реализации.
- Если GitHub Action OpenCode научится `schedule`, можно вернуться к
  стандартному режиму с `id-token`; сейчас CLI — единственный рабочий путь.
- Отчёты не попадают в коммиты: `contents: read` запрещает push, а рабочее
  дерево после агента очищается. Локальные отчёты складываются в игнорируемые
  `audit-reports/` и `.audit/`.
